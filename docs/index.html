Code that was run before it reached you.

Generated code often arrives with a missing import, a type error, a crash on startup or a leaked key, and you find out when you run it. This skill makes Claude build, test and start the code in its sandbox first, fix what breaks, and tell you plainly what was and was not verified.

What it actually runs

Every claim in Claude’s final note comes from the exit code and log of one of these scripts, not from Claude’s confidence. Python 3.11+ is the only requirement, and the scripts use the standard library only.

ScriptWhat it does
verify.pyDetects Node, Python, Go, Rust, Java, .NET, PHP, Ruby, Elixir, Dart/Flutter, Swift, C/C++ and Deno (monorepos and workspaces too; plain files get a syntax check) and runs install, typecheck, lint, build and tests, recording exit codes and failure output.
check_imports.pyFinds imports that are missing from package.json, requirements.txt or pyproject.toml, the bug that only shows up on a clean install.
smoke_test.pyStarts the app for real and requests its routes on 127.0.0.1, to catch crashes a build does not.
secret_scan.pyLooks for hardcoded API keys, tokens, private keys and committed .env files. Matches are masked in the output.
changed_files.pySnapshots your original files, then lists exactly which ones are new, modified or deleted.
make_zip.pyPacks only the changed files with repo-relative paths, and refuses to create the ZIP if a secret is found.

How a task goes

The effort scales with the task: a one-line regex is run once, a multi-file feature gets the full workflow.

  1. Mirror your repo and take a snapshot before anything is edited.
  2. Run the checks, read the failures, fix the root cause and run again. It stops after about five rounds on the same error and tells you what is stuck.
  3. Check imports against the dependency manifest.
  4. Smoke test anything that serves requests.
  5. Say what cannot be verified: live payment or auth APIs, your database, real secrets, browser-only behaviour.
  6. Deliver the code in the reply, or a ZIP of only the changed files.
  7. End with a short verification note taken from the real script output.

It does not make a check pass by cheating: no @ts-ignore, deleted tests or loosened assertions unless you approve.

Install

Claude (web, desktop, mobile)

Download verified-code-delivery.skill from the latest release, then upload it in Claude’s Skills settings. Then just ask Claude to write, fix or refactor code.

Tip: say “verify it and give me a ZIP of the changed files” to get the full workflow.

Claude Code

Copy the skill folder into your skills directory.

git clone https://github.com/gdigitalworld/Verified-code-delivery
cp -r Verified-code-delivery/skills/verified-code-delivery ~/.claude/skills/

Or run the scripts by hand

python scripts/verify.py ./my-project
python scripts/verify.py ./my-monorepo --project apps/web --env-file apps/web/.env.example
python scripts/check_imports.py ./my-project
python scripts/secret_scan.py ./my-project

Linux and macOS are the main targets. On Windows the test suite passes natively except the symlink tests, which need Developer Mode; WSL is the safest choice.

Safety, stated plainly

This tool runs your project’s own install, build and test commands, so treat it like running that code yourself.

Built in

  • Symlinks are never followed, and nothing outside the project folder is read or packed.
  • Only 127.0.0.1 is ever contacted.
  • A ZIP is blocked when a secret is found.
  • Variables like PATH and NODE_OPTIONS are refused from env files.
  • Zero runtime dependencies. Releases are built reproducibly with a signed provenance attestation.

Limits

  • Not a malware sandbox. Use --ignore-scripts and your own isolation for code you do not trust.
  • The secret scanner is pattern-based and will miss secrets with no recognisable shape.
  • Live APIs, databases and deployments cannot be verified from a sandbox. The note says so.

Read the threat model. Report vulnerabilities privately, as described in SECURITY.md.
